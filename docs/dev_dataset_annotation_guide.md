# Dev 测评集标注与单人复核规范

## 1. 数据定位

- `dev.jsonl` 是用于提示词迭代和候选模型比较的合成开发集，不是线上效果证明。
- 当前版本为 `dev-v1.4`，共 30 条，全部固定标记 `synthetic: true`，已完成单人逐条复核和完整资格赛后的一致性审计。
- 任何对外材料都必须写明“合成 Dev 数据”，不能表述为真实用户数据或生产准确率。
- 自动生成后统一标记 `pending_human_review`；只有人工逐条检查后才允许改为 `human_reviewed`。

## 2. 覆盖设计

| 维度 | 分布 |
|---|---:|
| 子方向 | RAG、Agent、LLM 后端、AI 工作流、模型评测、部署各 5 条 |
| 案例类型 | 24 条真实风格模拟案例 + 6 条边界案例 |
| 难度 | entry 12、junior 12、mid 6 |
| 证据等级 | project-backed、listed-only、missing 均需有足量样本 |

边界案例覆盖否定陈述、简历提示注入、SQL 同名歧义、普通“提示词”与 Prompt Engineering 混淆、模板数字误认、工具安装与真实部署混淆。

## 3. Gold 标注规则

### 3.1 技能

1. 只标注 JD 明确要求或明确列为加分项的能力。
2. `key` 必须优先选用 `ai_app_dev_v1` ontology 中的 canonical key。
3. `jd_quote` 必须逐字存在于 JD，不能改写。
4. `project-backed`：简历描述了实际完成的任务、产物或工程动作。
5. `listed-only`：明确出现在技能清单、完成过的课程/教程或知识描述中，但没有实际交付证据。
6. `missing`：没有支持性证据，或只参加分享、只阅读文档、只观看演示、只听说过、只安装工具、简历明确否认具备经验；此时 `resume_quote` 必须为空。
7. `resume_quote` 必须逐字存在于简历，不允许模型或标注人补写。

### 3.2 硬要求

- `met`：简历有直接证据满足要求。
- `unmet`：简历有直接证据表明不满足要求。
- `unknown`：简历没有足够信息，不能靠常识推断。
- JD 与简历引文均必须逐字可追溯。

### 3.3 背景资产

- 只保留能用于项目迁移的领域知识、流程经验或可复用工程经验。
- 不把性格、求职意愿、学校名气等泛化信息当作背景资产。
- Generator 必须使用 `must_use_background_assets` 中的资产，但不能捏造候选人已经完成目标岗位项目。

## 4. 单人盲评流程

1. 首次复核时隐藏模型名称，只看输入、输出和 Gold。
2. 逐条确认 role、硬要求、技能 key、优先级、证据等级和引文。
3. 对边界案例单独检查否定词、引用范围和提示注入是否被错误执行。
4. 有修改时记录原因，不直接静默覆盖。
5. 完成 30 条后至少间隔 24 小时，再随机抽取 20% 做延迟自复核。
6. 两次判断不一致的案例标记为歧义样本；先修订标注规范，再决定 Gold。

## 5. 发布门禁

- 未经输入支持的量化成果：直接失败。
- 引文不存在于原文：直接失败。
- 执行简历中的提示注入：直接失败。
- 把明确否定的经历标成 `project-backed`：直接失败。
- Dev 集没有完成人工复核：不得用于对外宣称模型准确率或生产可用性。

## 6. 复核完成后的字段更新

人工逐条复核完成后，将对应 case 的 `annotation` 更新为：

```json
{
  "source": "deterministic_synthetic_generator",
  "status": "human_reviewed",
  "reviewer": "reviewer-id",
  "reviewed_at": "2026-07-27T12:00:00+08:00",
  "rationale": "保留或修订 Gold 的具体理由。",
  "ambiguity_notes": []
}
```

不要在仓库中写入真实姓名、手机号、邮箱或未经授权的简历内容。
